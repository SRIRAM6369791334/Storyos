# ADR-0006: Story Universe as Hard Data Isolation Boundary

> **Status:** Accepted
> **Date:** 2026-07-29
> **Deciders:** Chief Software Architect, Lead Developer
> **Supersedes:** None

---

## Context

StoryOS is a multi-tenant platform where creators, teams, and enterprise organizations manage multiple Story Universes simultaneously. A single organization may have dozens of Story Universes — separate narrative worlds for different IPs, different projects, or different experimental branches of a story. A large enterprise deployment hosts thousands of Story Universes belonging to different organizations.

Story Universe isolation is the mechanism that prevents data from one Story Universe appearing in another. The question is not whether to isolate — isolation is non-negotiable. The question is how isolation is implemented: as a configurable access control policy, as a role-based permission model, or as a structural architectural property that makes cross-universe access architecturally impossible regardless of configuration, roles, or code paths.

The stakes of getting this wrong are high. An IP leakage event — one organization's story knowledge appearing in another organization's query results, AI reasoning, or exports — is a catastrophic trust failure. It is potentially a legal event. At enterprise scale, where a single Story Universe may represent years of creative development and significant commercial value, even a single leakage incident can terminate customer relationships and trigger litigation.

This decision corresponds to **DD-006** in the System Architecture Document (`docs/architecture/architecture.md`) and Architectural Principle P9 (Security First) — security as a structural property, not a feature layer.

---

## Alternatives Considered

### Option A: Policy-Based Isolation (Configurable)

Story Universe isolation is implemented as an access control policy layer applied at query time. All Story Universe data lives in a shared data store. Each query is accompanied by a universe context that the policy layer uses to filter results to data belonging to the authorized universe. Organization and Universe settings can configure the granularity of this filtering — including options to enable intentional cross-universe data sharing for collaboration scenarios.

**Pros:**
- Flexible — enables intentional cross-universe collaboration features (shared characters, linked universes, derivative works referencing a canonical universe)
- Lower storage infrastructure complexity — single shared data stores are simpler to manage than partitioned per-universe stores
- Schema changes and migrations apply once to the shared store rather than per-universe
- Query optimization can span universe boundaries for platform-level analytics
- Simpler backup and recovery — a single store has a single backup procedure
- Cross-universe search (for organization admins wanting a global view) is straightforward

**Cons:**
- Policy misconfiguration is a credible risk at enterprise scale — a single incorrect permission setting can expose all data from one universe to unauthorized actors
- A software bug in the policy filter can produce cross-universe data leakage with no structural safeguard to prevent it — the policy is the only line of defense
- AI agents processing queries in Universe A could produce cross-universe leakage through context window contamination if their memory scoping is misconfigured — the policy layer is downstream of memory loading
- Configurable sharing creates an attack surface — any configuration interface for cross-universe access is a potential social engineering or misconfiguration target
- Enterprise customers in regulated industries (entertainment studios, game studios with licensed IP) cannot accept a shared-store model for their IP — regulatory and contractual IP protection requirements demand physical separation, not policy filtering
- In a multi-tenant scenario, one organization cannot independently verify that policy settings correctly prevent another organization from accessing their data — they must trust the platform's policy implementation and configuration
- At enterprise scale, the number of active policies grows quadratically with universe count, creating policy management complexity and audit surface area

---

### Option B: Role-Based Isolation

Story Universe isolation is implemented through a comprehensive role hierarchy. Each actor (human user, AI agent, plugin) has explicit role assignments per Story Universe. Data access is gated on role authorization checks at every query. Cross-universe access is prevented by ensuring no actor has authorized roles in more than one universe (except platform administrators). The Security Module enforces role checks on every operation.

**Pros:**
- Fine-grained — roles can be scoped very precisely (a collaborator can access Character data but not Workflow data in a specific universe)
- Established pattern — RBAC is well-understood and widely implemented in enterprise software
- Supports legitimate cross-universe scenarios through explicit role grants — an editor reviewing a derivative work can be granted a limited role in both the source and derivative universe
- Centralized role management — all access control is managed through the Security Module's role hierarchy
- Audit trail clearly records role grants and the operations they permitted
- Scales to complex organizational structures with multiple teams, roles, and partial access requirements

**Cons:**
- Role-based isolation is still policy-based isolation — it is subject to the same misconfiguration risk as Option A
- A user or AI agent assigned roles in multiple universes (even legitimately) creates a path for cross-universe knowledge to exist in the same session context — preventing cross-universe contamination requires careful session scoping logic in addition to role enforcement
- The Security Module's role resolution logic is code that can contain bugs — a bug in role resolution could grant cross-universe access without triggering an access control failure
- AI agents with multi-universe roles (e.g., a platform-level administrator agent) require extremely careful memory scoping — their role grants do not prevent cross-universe memory contamination unless the AI Layer enforces isolation independently of the Security Module
- At scale, role auditing becomes complex — verifying that no actor has unintended cross-universe access requires querying across all role assignments
- Does not eliminate the shared data store problem — even with perfect role enforcement, a single shared store means that data from all universes is physically co-resident, relying entirely on the role layer to maintain separation
- Platform administrators with cross-universe roles are a persistent insider threat surface — their legitimate access to multiple universes means they must be trusted not to extract and share data between them

### Option C: Structural Isolation — Architecturally Prevented Cross-Universe Access *(Selected)*

Each Story Universe's data is stored in a physically isolated partition. The data storage architecture partitions entity stores, graph stores, document stores, version stores, and media stores by Story Universe. Cross-universe data access is not prevented by a policy check or a role check — it is prevented by the fact that the data path from one universe's partition to another's does not exist. An AI agent's Memory Graph is loaded exclusively from its assigned universe's partition. A query against Universe A's Graph Store cannot reach Universe B's Graph Store through any query path. Intentional cross-universe data movement (for legitimate derivative work or export scenarios) requires an explicit, audited export-and-import operation — a deliberate data transfer, not a query.

**Pros:**
- Isolation is an architectural invariant, not a policy setting — it cannot be misconfigured because there is no configuration option for cross-universe data access
- Eliminates an entire class of security vulnerabilities — policy misconfiguration, role assignment bugs, and access control logic errors cannot produce cross-universe leakage because the data paths do not exist
- AI agent memory scoping is structurally enforced at the data partition level — an agent initialized for Universe A physically cannot access Universe B's partition regardless of its configured scope
- Enterprise IP protection requirements are satisfied without reliance on policy correctness — auditors can verify data isolation through infrastructure inspection rather than policy review
- Data sovereignty and regulatory compliance are simplified — each universe partition can be independently managed for data residency, retention, and compliance requirements
- Organizations can independently verify their universe isolation by inspecting partition boundaries — they do not need to trust the platform's policy implementation
- Scales naturally — new Story Universe partitions are provisioned at creation time and are independent of all existing partitions
- Aligns with Architectural Principle P9 (Security First) — security as a structural property at every layer

**Cons:**
- Cross-universe data movement for legitimate scenarios (derivative works, character re-use across IPs) requires a formal export-and-import operation — cannot be accomplished with a simple query
- Higher storage infrastructure complexity — per-universe partitioning requires partition management, provisioning automation, and per-partition backup and recovery procedures
- Schema migrations must apply across all universe partitions — migrating a schema change to a platform with thousands of universe partitions requires robust migration tooling and careful orchestration
- Platform-level analytics and reporting (aggregated across all universes for organizational dashboards) require cross-partition aggregation infrastructure that must enforce the isolation boundary for read-only aggregation without creating data leakage paths
- Partition provisioning adds latency to Story Universe creation — the platform must provision storage infrastructure before a new universe is ready for use
- Cold universe optimization (very low-activity universes) requires archiving strategies that work at the partition level

---

## Decision

Story Universe isolation is implemented as a structural architectural property. Each Story Universe's data is stored in a physically isolated partition. No query, AI operation, or data access path crosses universe partition boundaries. Cross-universe data movement requires explicit, audited export-and-import operations. The isolation boundary is enforced at the storage partition level, not the policy or role level.

---

## Rationale

The platform's core value proposition — that StoryOS is the most trusted home for a creator's story knowledge — is directly dependent on creators and organizations being certain that their story universes cannot leak into other universes, other organizations, or other users' AI sessions. This certainty cannot be delivered by a policy layer, regardless of how well-implemented that policy layer is. Policies can be misconfigured. Code can have bugs. Administrators can make mistakes. These are irreducible facts of operating software at enterprise scale.

The only isolation model that eliminates this risk class entirely is structural isolation — making cross-universe access architecturally impossible rather than policy-prevented. If the data paths between universe partitions do not exist, then no misconfiguration, no bug, and no insider action can cause cross-universe leakage through those paths. The isolation is verifiable through infrastructure inspection rather than policy review.

Option A (policy-based) and Option B (role-based) are both forms of the same approach: use software logic to prevent cross-universe access in a system where cross-universe data paths physically exist. Both carry the risk of policy/logic failure. At enterprise scale, a platform that has served thousands of universes over years is certain to encounter edge cases in its access control logic. The question is whether those edge cases result in access control failures (Option A and B) or nothing (Option C).

The friction of export-and-import for cross-universe data movement is deliberate. The platform could provide convenience features for cross-universe data transfer, but any such feature must be an explicit, audited, intentional action — not a query that crosses a partition boundary. This friction protects creators from inadvertent cross-universe contamination and creates a complete audit record of every intentional data transfer between universes.

---

## Consequences

### Positive
- Cross-universe data leakage is architecturally impossible — not a policy risk to be monitored, but a structural property to be verified once
- Enterprise customers can independently verify universe isolation through infrastructure inspection — the platform's security claim is observable, not just asserted
- AI agent memory scoping is enforced at the data partition level — no agent initialization bug or scope configuration error can cause cross-universe memory contamination
- Regulatory compliance for data residency and sovereignty is simplified — each universe partition can be independently managed per jurisdiction
- Each universe partition scales, archives, and migrates independently — no universe's growth affects other universes' operational characteristics
- Partition isolation provides natural blast radius containment — a data corruption event in one universe's partition cannot propagate to other universes

### Negative / Trade-offs
- Legitimate cross-universe scenarios (derivative works, character licensing across IPs) require explicit export-and-import operations — no in-system direct reference or query path
- Storage infrastructure complexity scales with universe count — partition management, provisioning automation, and per-partition backup procedures require dedicated infrastructure investment
- Schema migrations across all universe partitions require robust migration orchestration — thousands of partitions cannot be migrated manually; automated migration tooling is a platform requirement, not optional
- Universe creation latency includes partition provisioning time — instantaneous universe creation is not achievable; provisioning must be fast enough to feel immediate (target: under 10 seconds) but is not truly zero-cost
- Platform-level analytics (global usage reporting, aggregate entity counts across all universes for organizational admins) require cross-partition read aggregation infrastructure that must be carefully designed to not create leakage paths
- Cold storage archiving for inactive universes must operate at the partition level — archiving a low-activity universe is more complex than archiving a few rows in a shared table

## Compliance

Future developers verify this decision is being respected by confirming the following:

1. **Storage layer enforces partition isolation**: Each of the six storage stores (Entity Store, Graph Store, Document Store, Media Store, Version Store, Audit Store) must be implemented with Story Universe partitioning as a structural property. All query interfaces must require a universe partition context and must be incapable of returning results from a different partition.
2. **No cross-partition query paths exist**: Code review must verify that no query builder, ORM method, or storage interface includes a parameter or path that allows querying across multiple universe partitions in a single operation (except explicitly designed aggregation interfaces, which must be separately reviewed).
3. **AI agent initialization requires a single universe partition context**: The AI Memory Manager must load Memory Graph data exclusively from one universe partition per agent session. An agent initialized for Universe A must not be able to query Universe B's partition through any Memory Manager interface.
4. **Cross-universe data movement is export-and-import only**: Any feature that moves data from one universe partition to another must be implemented through the Export Engine and Import Pipeline, with full audit records on both sides. Direct partition-to-partition copy operations are prohibited.
5. **Partition provisioning is automated and consistent**: Story Universe creation must include automated partition provisioning across all six storage stores. Manual partition creation is prohibited — all partitions must be provisioned through the same automated provisioning pipeline to ensure consistent structure and isolation properties.
6. **Architecture review gate**: Any new feature proposal that involves cross-universe data access, sharing, or referencing must be escalated to the Chief Software Architect for review against this ADR. Features that attempt to create query-time cross-universe access must be rejected and redesigned to use export-and-import.
