# ADR-0001: Knowledge Graph as Central Architectural Model

> **Status:** Accepted
> **Date:** 2026-07-29
> **Deciders:** Chief Software Architect, Lead Developer
> **Supersedes:** None

---

## Context

StoryOS needed a foundational data representation model — the core organizing structure around which all modules, AI operations, and storage strategies would be built. This was the single most consequential architectural decision on the platform, because it shapes every downstream choice: how entities are stored, how AI agents reason, how consistency is enforced, and how creators query their story world.

Three fundamentally different paradigms were evaluated. The choice had to account not only for present requirements (entity management, AI consistency checking, workflow) but for the long-term direction of the platform toward enterprise-scale IP management and AI-native narrative intelligence.

The decision directly corresponds to **DD-001** in the System Architecture Document (`docs/architecture/architecture.md`).

---

## Alternatives Considered

### Option A: Document-Centric Model

Story data is organized around textual documents — chapters, scenes, and notes. Entities (characters, locations, events) are referenced within documents as tagged text spans or simple metadata fields. The document is the primary record; structured data is derived from it.

**Pros:**
- Familiar mental model for writers — documents are the primary artifact of the writing process
- Simpler initial data model; lower engineering complexity in early phases
- Many mature tooling options (document databases, rich-text editors, CMS platforms)
- Natural fit for output formats — documents map directly to manuscripts, scripts, and outlines
- Lower onboarding barrier for non-technical creators

**Cons:**
- Relationships between story elements are implicit, buried in text, not queryable
- AI reasoning over relational story knowledge requires reconstructing structure from documents on every query — computationally expensive and error-prone
- Consistency checking across entities requires parsing every document for every check — does not scale
- No native concept of "entity truth" — the same character may be described differently across twenty documents with no way to detect contradiction except by human reading
- Cannot support graph traversal queries (e.g., "find all characters within two relationship degrees of X who were present at events involving faction Y") without a separate indexing layer that essentially rebuilds a graph anyway
- AI memory is naturally entity-scoped, not document-scoped — forcing AI agents to reason over documents rather than structured knowledge creates a fundamental mismatch

---

### Option B: Entity List Model

Story data is organized as flat collections of entity records — lists of characters, locations, events, factions, etc. Each entity type has a defined schema with typed attribute fields. Relationships between entities are stored as foreign-key-style reference fields on each record.

**Pros:**
- Clear, structured representation of individual entities with typed attributes
- More queryable than the document model for single-entity lookups
- Easier to validate individual entity data at the record level
- Familiarity to developers — maps naturally to relational database tables
- Simpler to build initial CRUD interfaces and forms for entity data entry
- Enforces schema discipline — entities cannot have arbitrary free-form attributes without explicit schema additions

**Cons:**
- Relationships are second-class citizens: stored as ID references, not as first-class typed, directed, attributed edges
- Multi-hop relationship traversal (e.g., "how is Character A connected to Location B through any path?") requires expensive join operations or application-layer graph reconstruction
- Relationship history (how did a relationship between two characters change across events?) is not naturally representable — requires additional audit tables
- Temporal relationship scoping (a relationship that existed only between events E1 and E4) is complex to model and query
- Consistency checking across relationship chains requires bespoke query logic per check type, not generalizable graph algorithms
- Does not scale gracefully as relationship complexity grows — a mature story universe has thousands of relationships of dozens of types; flat entity lists cannot represent this with acceptable query performance
- AI reasoning is inherently graph-structured — forcing AI to translate list-based queries into relationship chains reintroduces the complexity the model tried to remove

---

### Option C: Knowledge Graph Model *(Selected)*

Story data is represented as a property graph: entities are typed nodes with attribute sets, and relationships are typed, directed, attributed edges between nodes. The entire story universe is a single interconnected graph. Canon status, provenance, and temporal scope are first-class properties on both nodes and edges.

**Pros:**
- Relationships are first-class citizens — relationship types, attributes, history, and directionality are natively representable
- Graph traversal queries are natural and efficient — multi-hop queries, path-finding, and subgraph extraction are core graph database operations
- AI reasoning maps directly to graph operations — most AI reasoning tasks (consistency checking, relationship inference, entity disambiguation) are graph problems
- Temporal relationship scoping is native — edges carry temporal context as first-class attributes
- Knowledge provenance is native — edge properties carry source content, extraction method, and Canon confirmation status
- Consistency validation generalizes — contradiction detection is a graph property check, applicable across all entity types without per-type code
- Supports point-in-time snapshots of the complete story universe state
- Aligns with the long-term Universal Story Graph vision (Section 11.3, architecture.md) — the platform's knowledge graph can eventually contribute to cross-universe narrative intelligence

**Cons:**
- Significantly more complex initial data model than documents or entity lists
- Graph databases are less universally familiar than relational databases — steeper learning curve for the engineering team
- Graph schema evolution requires careful migration planning — changing relationship types or node structures impacts traversal queries
- Higher write complexity — every entity creation must register in the graph, not just write to a table
- Performance tuning for large graphs requires specialized expertise (index strategies, query planning, partition design)

---

## Decision

The Knowledge Graph model is adopted as the central architectural representation for all story knowledge in StoryOS. Every entity is a graph node; every relationship is a typed, directed, attributed graph edge. The Knowledge Graph is the authoritative source of story truth, and all AI operations, consistency checks, and cross-entity queries are executed against it.

---

## Rationale

Story knowledge is fundamentally relational at every level — characters relate to events, events relate to locations, factions relate to characters, world rules constrain entity behaviors. Any architecture that treats these relationships as secondary — as foreign key references or text annotations — fails to represent the actual structure of the domain.

The document-centric model is appropriate for tools whose primary output is documents. StoryOS's primary output is structured story knowledge from which documents are derived — the inversion is deliberate and critical. The entity-list model improves on documents by structuring individual entities but still treats relationships as an afterthought. When relationship complexity grows to production-story scale (thousands of characters, events, and locations with hundreds of relationship types), the entity-list model collapses under join complexity and fails to support the graph-native reasoning patterns AI agents require.

The knowledge graph model aligns architectural structure with domain structure. The additional complexity is front-loaded in the data model and absorbed by the Knowledge Layer — every module above it benefits from native graph query capability, AI agents get a reasoning surface that matches their inference patterns, and consistency validation becomes a generalizable operation rather than a bespoke feature per entity type.

The long-term trajectory of the platform — Universal Story Graph (Year 3–4), Platform Intelligence API (Year 5–7) — is only viable on a graph foundation. Adopting a simpler model now would require a complete data architecture migration at exactly the moment the platform is scaling to enterprise volume.

---

## Consequences

### Positive
- All relationship types — character-to-character, character-to-event, event-to-location, faction-to-concept — are queryable with equal power and without bespoke code per type
- AI consistency checking, inference, and memory are graph-native operations — no translation layer between AI reasoning and data representation
- Multi-hop traversal queries that would be prohibitively expensive in a relational model are efficient graph operations
- Knowledge provenance (where did this fact come from?) is a first-class graph property, not a separate logging concern
- The graph model supports point-in-time snapshots, enabling the Versioning System to capture complete story-universe states
- Architectural alignment with the long-term Universal Story Graph and intelligence API roadmap
- Canon status as a first-class graph property enables clean separation between confirmed truth and AI-proposed inference

### Negative / Trade-offs
- Significantly higher initial data model complexity — requires a dedicated Knowledge Layer with specialized graph storage (Graph Store)
- Engineering team requires graph database expertise that is less common than relational database expertise — hiring and training investment required
- Graph schema evolution requires disciplined migration planning — relationship type changes affect traversal query logic platform-wide
- Write operations are more complex and slower than simple record inserts — every entity creation triggers graph registration, consistency validation, and provenance tracking
- Debugging graph-level issues (incorrect traversal results, provenance chain breaks) requires specialized tooling and graph-oriented mental models
- Higher infrastructure cost at early scale than a document or relational solution would require

---

## Compliance

Future developers verify this decision is being respected by confirming the following:

1. **No direct entity cross-referencing outside the graph**: Domain modules must never store entity relationships as simple ID references in their own schemas. All inter-entity relationships must be registered as edges in the Knowledge Graph Module.
2. **All AI reasoning routes through the Knowledge Layer**: AI agents must read story knowledge from the Memory Graph (a Canon-synchronized view of the Knowledge Graph), never by querying Domain Module storage directly.
3. **Consistency checks are graph operations**: Contradiction detection in the Consistency Validator must be implemented as graph property checks, not as ad-hoc per-entity-type comparison logic.
4. **Architecture review gate**: Any new module proposal that introduces entity-to-entity relationships must demonstrate how those relationships are represented as Knowledge Graph edges before the module design is approved.
5. **Graph Store is the authoritative relationship record**: If any discrepancy exists between an entity's relationship data in a Domain Module's own store and the Knowledge Graph, the Knowledge Graph record is authoritative.
