# ADR-0003: Immutable Audit Trail with Cryptographic Chaining

> **Status:** Accepted
> **Date:** 2026-07-29
> **Deciders:** Chief Software Architect, Lead Developer
> **Supersedes:** None

---

## Context

StoryOS is an enterprise platform managing intellectual property that belongs to creators and organizations. It hosts AI agents whose actions must be attributable, reviewable, and contestable. It handles compliance obligations for enterprise customers who may be subject to regulatory audit requirements. It also needs to protect itself and its users against insider threats — including administrative access.

The audit system is the foundation of platform trust. The central design question was: what level of integrity guarantee should the audit trail provide, and what architectural properties must the audit store have to deliver that guarantee?

The answer to this question is not separable from questions about how the platform presents itself to enterprise customers, how it handles security incidents, and whether AI agent accountability is genuine or superficial. A platform that allows audit records to be modified — even by administrators, even with good intentions — does not have an audit trail; it has a suggestion log.

This decision corresponds to **DD-003** in the System Architecture Document (`docs/architecture/architecture.md`).

---

## Alternatives Considered

### Option A: Mutable Audit Log in General-Purpose Database

Audit events are written as records in a standard database table alongside other application data. Records have timestamps and actor fields. Administrators with database access can update or delete records if needed (for data corrections, legal holds, or storage management). The log is searchable and queryable through standard database mechanisms.

**Pros:**
- Simplest implementation — standard database INSERT operations; no specialized infrastructure
- Easy to correct errors — a wrongly recorded event can be updated or removed
- Storage management is straightforward — old records can be pruned on a retention schedule
- Queryable through standard SQL — no specialized query tooling required
- Integrates naturally with general-purpose reporting and analytics pipelines
- Low infrastructure overhead — shares database with application data

**Cons:**
- A mutable audit log is not an audit log — it is a table of records that happened to be written during operations. It provides no evidence of what actually occurred if records can be changed after the fact
- Provides zero protection against insider threats — any administrator with database access can alter or delete evidence of their own actions
- Does not satisfy enterprise compliance requirements (SOC 2, ISO 27001, GDPR audit trail standards) that require immutable, tamper-evident records
- An attacker who gains database access can silently eliminate evidence of their actions
- Cannot prove to a creator that an AI agent's action record has not been modified after the fact — undermines the entire AI accountability model
- In a legal or compliance dispute, a mutable audit log has no evidentiary value — it cannot demonstrate that the record reflects what actually happened

---

### Option B: Append-Only Log in Isolated Store (Without Cryptographic Chaining)

Audit records are written to a dedicated, append-only store that is physically separated from the application database. The store's write interface accepts only INSERT operations — UPDATE and DELETE operations are not implemented. The store is accessible only through a dedicated access layer requiring Super Admin authorization. Records are timestamped and sequenced but not cryptographically linked.

**Pros:**
- Append-only enforcement prevents standard write operations from modifying existing records
- Physical isolation from application data prevents casual administrative access from touching audit records
- Significantly stronger than a mutable log for most practical threat scenarios
- Simpler to implement than cryptographic chaining — no hash computation per record
- Meets many baseline audit requirements for regulatory compliance
- Still supports retention-based archiving to cold storage for older records
- Dedicated store allows independent scaling of audit write throughput

**Cons:**
- Append-only enforcement is an application-level constraint — someone with direct infrastructure access (database administrator, cloud console access, infrastructure engineer) can still modify or delete records at the storage layer
- Without cryptographic chaining, there is no way to detect whether a sequence of records has been tampered with even if individual records have not been visibly modified
- Record insertion order tampering (inserting records with falsified timestamps to fill gaps) is undetectable
- Does not provide a cryptographically provable integrity guarantee — in a dispute, the platform can assert records are unmodified but cannot prove it mathematically
- Does not meet the highest tier of enterprise compliance requirements that explicitly require cryptographic integrity proofs on audit trails
- AI agent accountability remains soft — the platform cannot produce cryptographic proof that an agent's recorded actions were not altered after the fact

---

### Option C: Cryptographically Chained Append-Only Log in Isolated Store *(Selected)*

Audit records are written to a dedicated, physically isolated append-only store. Each record contains a cryptographic hash of the previous record's content plus its own payload — forming a hash chain identical in principle to blockchain record-keeping. Any modification of any record in the chain — including changes to timestamps, actor fields, or operation content — causes hash verification to fail for all subsequent records, making tampering mathematically detectable. The store enforces append-only at the interface level and is accessible only through a dedicated Super Admin access layer.

**Pros:**
- Tamper-evidence is mathematically provable, not just operationally asserted — the hash chain makes record modification detectable regardless of who performed it
- Provides cryptographic proof that a sequence of events occurred in the recorded order with the recorded content — usable as evidence in compliance audits, legal disputes, and security investigations
- Protects against insider threats including administrative access — even the platform operator cannot silently modify audit records without breaking the hash chain
- Meets the highest tier of enterprise compliance requirements for audit trail integrity
- Provides concrete, demonstrable protection to creators: their AI agent's action history is cryptographically sealed
- Detection of any tampering is automated — routine hash chain verification exposes any compromise
- Aligns with the platform's principle P9 (Security First) — security as a structural property, not a feature layer

**Cons:**
- Hash computation adds latency to every audit write operation — acceptable but non-zero cost
- Chain repair after legitimate data migrations or emergency data corrections requires a formal, auditable re-chaining process — cannot simply UPDATE a record
- Audit storage grows indefinitely without the ability to compact or prune — old records cannot be deleted without breaking the chain (full chain archiving to cold storage is the accepted mitigation)
- Verification of the full chain is computationally intensive — routine spot-checks are practical, but full chain verification is an expensive maintenance operation
- More complex implementation than append-only alone — requires hash computation, chain head management, and verification infrastructure
- Recovery from accidental chain corruption (infrastructure failure during a write) requires a defined recovery protocol

---

## Decision

The audit log is implemented as an append-only, cryptographically chained sequence of records stored in a dedicated Audit Store that is physically isolated from all application data. Each record contains the cryptographic hash of the preceding record. The Audit Store is accessible only through a dedicated access layer requiring Super Admin authorization. No path exists through the application to modify or delete audit records.

---

## Rationale

The platform's audit trail serves three distinct purposes, each of which demands immutability:

**Creator trust**: Creators using StoryOS must be able to trust that the record of what AI agents did to their story knowledge is accurate and unaltered. If an AI agent proposed a controversial Canon change, the creator must be able to examine the complete, unmodified record of that agent's reasoning. A mutable audit log cannot provide this guarantee.

**Enterprise compliance**: Enterprise customers are subject to compliance frameworks (SOC 2 Type II, ISO 27001, GDPR Article 5) that require audit trails to be tamper-evident and verifiable. Append-only without cryptographic chaining satisfies some of these requirements but not the highest tier. Cryptographic chaining provides a mathematically demonstrable integrity guarantee that satisfies all relevant compliance frameworks.

**Security incident response**: When a security incident occurs, the first question is "what happened?" A compromised audit log makes that question unanswerable. Cryptographic chaining ensures that even if an attacker gained infrastructure access, any modifications to the audit record are detectable — the platform cannot be made to appear that nothing happened.

Option A fails all three purposes. Option B satisfies practical requirements but cannot produce cryptographic proof and remains vulnerable to infrastructure-level tampering. Option C is the only option that satisfies creator trust, compliance, and incident response simultaneously.

The consequence of indefinite storage growth is accepted. Audit completeness is more valuable than storage efficiency. Cold storage archiving of old audit chains satisfies both cost management and compliance requirements without compromising integrity.

---

## Consequences

### Positive
- The platform can produce cryptographically verifiable proof that an audit record has not been modified — usable in compliance audits, legal proceedings, and creator disputes
- Insider threats targeting audit records are detectable — no actor, including platform administrators, can silently alter audit history
- All AI agent actions are sealed in the audit chain — AI accountability is a mathematical guarantee, not an operational promise
- Routine hash chain verification provides continuous integrity monitoring — tampering is detected immediately rather than discovered only during incident investigation
- The platform satisfies the highest tier of enterprise compliance requirements for audit trail integrity from day one
- The dedicated, isolated Audit Store is independently scalable and has no operational coupling to application data performance

### Negative / Trade-offs
- Every audit write incurs hash computation latency — audit throughput is bounded by hash computation speed and must be accounted for in write path performance budgets
- Audit storage grows without bound — retention management must use cold storage archiving, not deletion
- Data corrections to audit records (e.g., a record written with incorrect actor attribution due to a bug) cannot be performed silently — corrections require a formal re-chaining process that is itself fully auditable
- Full chain verification is computationally expensive — routine maintenance uses spot-check verification; full chain scans are periodic and scheduled, not continuous
- Chain head management requires careful concurrency handling — parallel write paths must be serialized at the chain head to prevent forks
- Emergency data recovery procedures for the Audit Store are more complex than for standard application data stores — recovery operations must preserve chain integrity

## Compliance

Future developers verify this decision is being respected by confirming the following:

1. **Audit Store is write-once only**: The Audit Store interface must expose only INSERT operations. No UPDATE or DELETE operation may be implemented against the Audit Store through any path, including administrative tooling.
2. **Every record includes the predecessor hash**: The Audit System's record writer must compute and embed `SHA-256(previous_record_payload)` in every new record before committing. Records without a valid predecessor hash reference must be rejected by the store interface.
3. **Audit Store is physically isolated**: The Audit Store must reside in a separate physical storage partition from all application stores (Entity Store, Graph Store, Document Store, Version Store). Shared-storage configurations are prohibited.
4. **Access is Super Admin gated**: The Audit Store access layer must enforce Super Admin role verification on every read and write request. No standard user, Organization Admin, or AI agent role may access the Audit Store directly.
5. **Chain integrity verification is scheduled**: Operations must include a scheduled chain verification process (hash re-computation from chain origin) that runs at a defined frequency and alerts on any verification failure.
6. **Audit writes are synchronous to the operation**: The Audit System must record an operation before the operation's completion response is returned to the calling actor. Asynchronous audit writes are prohibited — they create windows where operations exist without audit records.
