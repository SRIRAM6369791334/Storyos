# ADR-0002: AI Agents as First-Class System Peers

> **Status:** Accepted
> **Date:** 2026-07-29
> **Deciders:** Chief Software Architect, Lead Developer
> **Supersedes:** None

---

## Context

StoryOS requires AI capabilities — consistency checking, entity extraction, dialogue generation, timeline validation, and workflow review — as core platform features, not optional add-ons. The fundamental architectural question was: how are AI agents integrated into the system model?

The range of integration approaches spans from treating AI as a purely external utility (a service called via API when needed) to treating AI agents as first-class system actors governed by the same identity, authorization, memory, and audit infrastructure as human users. Each integration model has profound consequences for platform security, auditability, AI reliability, and long-term extensibility.

This decision directly determines whether the platform's AI capabilities can scale with enterprise trust requirements and whether creators can hold AI to account for its actions. It corresponds to **DD-002** in the System Architecture Document (`docs/architecture/architecture.md`).

---

## Alternatives Considered

### Option A: External AI Service Integration (API Call Model)

AI capabilities are provided by external AI services (cloud API providers or self-hosted models) called synchronously when needed. Domain modules or the Application Layer make direct API calls to AI endpoints, pass relevant context in the request, receive a response, and process it inline. AI has no persistent state, no system identity, and no access control integration.

**Pros:**
- Lowest initial engineering complexity — integration is a standard HTTP client call
- No dedicated AI Layer required; AI is just another dependency of calling modules
- Easy to swap AI providers by changing API endpoints
- No persistent infrastructure for AI state management
- Rapid time-to-first-AI-feature
- Standard pattern familiar to most engineering teams

**Cons:**
- AI has no identity in the system — there is no actor record for "who made this AI suggestion," only "the system did something"
- No audit trail for AI reasoning steps — the system cannot answer "why did the AI flag this contradiction?" because the reasoning was ephemeral
- No persistent memory — AI starts every session cold, with no knowledge of the story universe built up over previous interactions. This requires passing the entire relevant context in every API call, which is expensive, incomplete, and fundamentally unscalable for large story universes
- No role-based access control for AI — cannot enforce "this AI agent may only read Characters in Universe X" without building a bespoke permission layer outside the standard security infrastructure
- Cross-session consistency is impossible — an AI agent that reviewed Chapter 3 last week has no memory of it when reviewing Chapter 7 today
- No scope enforcement — the API call pattern has no mechanism to prevent an AI request from being constructed with data from multiple unauthorized universes
- No audit integrity — AI actions cannot be included in the tamper-evident audit chain because there is no AI actor record to attach them to

---

### Option B: Managed AI Service Layer (Middleware Model)

A dedicated AI middleware service sits between the platform and AI providers. This middleware manages session context, rate limiting, and basic logging, but AI agents are still stateless in terms of story knowledge — context is assembled and injected per call. AI agents are not system actors; they are services the middleware invokes. The middleware exposes a simplified AI API to platform modules.

**Pros:**
- Centralizes AI integration logic — platform modules call middleware, not raw AI APIs
- Provides a single point of control for rate limiting, provider switching, and error handling
- Supports basic request logging through the middleware layer
- More maintainable than scattered API calls across domain modules
- Supports some level of context aggregation (middleware can assemble relevant story context before calling the AI provider)
- Allows provider independence — the middleware abstracts which AI model is used

**Cons:**
- AI agents are still stateless regarding story knowledge — the middleware injects context per call rather than maintaining a persistent Memory Graph
- AI still has no system identity — middleware-generated AI calls appear in audit logs as "system" events, not as attributed agent actions
- Authorization enforcement is still bespoke — the middleware must implement its own access control logic parallel to the Security Module, creating duplication and a risk of inconsistency
- Cross-session memory continuity requires the middleware to manage a context store, effectively reinventing the AI Memory Module without the governance structures the platform provides
- AI reasoning steps are logged only at the middleware level — they are not part of the platform's tamper-evident audit chain
- AI agents cannot participate in workflow stages as first-class reviewers because they have no system role and cannot be assigned workflow permissions
- As AI agent types proliferate (Character Agent, Timeline Agent, World Agent), middleware complexity grows proportionally with no architectural containment

---

### Option C: AI Agents as First-Class System Peers *(Selected)*

AI agents are implemented as authenticated system actors governed by the platform's identity, authorization, and audit infrastructure, equivalent in structural treatment to human users. Each agent type has a defined system role, a scoped access context per Story Universe, and a persistent Memory Graph synchronized with Canon. All AI actions — reads, reasoning steps, proposals, memory writes — are logged in the tamper-evident Audit System under the agent's identity. AI agents participate in workflows as assignable reviewers. A dedicated AI Layer manages agent lifecycle, memory, and inference coordination.

**Pros:**
- Every AI action is attributed to a specific agent with a specific role — "Character Agent on Universe X proposed this Canon change at 14:32 based on these reasoning steps" is fully auditable
- Role-based access control applies to AI agents identically to human users — an agent scoped to Universe X cannot access Universe Y by any architectural path
- Persistent Memory Graph eliminates the context-injection problem — agents have continuous, synchronized knowledge of their assigned story universe across all sessions
- AI agents can be assigned as workflow stage reviewers with the same permission model as human reviewers
- Agent memory is inspectable by creators at any time — full transparency into what the AI knows about a story
- The audit trail includes AI reasoning steps as linked entries — complete forensic capability over AI behavior
- The Security Module's scope enforcement applies to AI agents without bespoke code — they are just actors with roles
- Aligns with enterprise compliance requirements — AI actions are as auditable and attributable as human actions
- Foundation for the AI agent plugin ecosystem described in Section 7.4 of architecture.md — third-party AI agents can be governed by the same infrastructure

**Cons:**
- Requires a dedicated AI Layer with significant engineering investment (Agent Orchestrator, AI Memory Manager, Inference Engine, AI Audit Logger)
- Agent lifecycle management (initialization, scope assignment, synchronization, termination) adds operational complexity
- Memory Graph synchronization must be kept consistent with Canon — synchronization logic is non-trivial at scale
- Higher infrastructure cost — persistent Memory Graphs per universe per agent type require dedicated storage and compute
- Debugging AI agent behavior is more complex than debugging a stateless API call — requires reasoning log analysis and memory state inspection

---

## Decision

AI agents are implemented as first-class system peers with system-level identities, role-based access control, scoped persistent memory, and full audit trail participation. A dedicated AI Layer (Agent Orchestrator, AI Memory Manager, Inference Engine, AI Audit Logger) governs all agent operations. No AI reasoning or action occurs outside this layer's governance.

---

## Rationale

The external service and middleware models both fail the platform's enterprise trust requirements for the same underlying reason: AI actions are unattributed, unscoped, and unauditable at the level the platform demands. An enterprise creator paying to protect their intellectual property cannot accept a platform where AI actions are logged only as "the system did something" — they need to know which agent, in which universe, took which action, based on which knowledge, at which time.

The first-class system peer model is the only integration pattern that satisfies these requirements without building a parallel governance system outside the platform's own infrastructure. By treating AI agents as actors governed by the Security Module and Audit System, the platform gets attribution, scoping, and auditability for free — the same mechanisms already required for human users.

Persistent Memory Graphs are not a luxury feature; they are a prerequisite for AI agents to be genuinely useful in a story universe with thousands of entities built up over months of work. A stateless agent injecting context per call will always be limited to whatever context fits in its token window. A persistent Memory Graph synchronized with Canon gives the agent full story knowledge — the same knowledge the creator has.

The higher architectural complexity of this approach is real and accepted. The complexity is contained within the AI Layer, which has clear boundaries and interfaces. All modules above it benefit from AI agents that are reliable, attributable, and controllable — far preferable to capable-but-opaque AI that erodes creator trust over time.

---

## Consequences

### Positive
- Every AI action is fully auditable — agent identity, scope, reasoning steps, proposals, and outcomes are all part of the tamper-evident audit chain
- Story Universe isolation applies to AI agents structurally — a scoped agent cannot access data outside its assigned universe through any architectural path
- AI agents maintain continuous story knowledge across sessions — consistency checking does not degrade as the story grows
- Creators can inspect agent memory state at any time — full transparency eliminates the "black box" problem
- AI agents participate in workflow stages as first-class reviewers — AI review is a governed, auditable part of the production pipeline
- Third-party AI agent plugins are governed by the same infrastructure — no special-case security handling for third-party agents
- The AI safety boundaries in Section 6.4 of architecture.md (agents cannot write to Canon, agents cannot access unauthorized universes) are architectural invariants enforced by the AI Layer, not policy settings that can be misconfigured

### Negative / Trade-offs
- A dedicated AI Layer with four major components (Agent Orchestrator, AI Memory Manager, Inference Engine, AI Audit Logger) represents significant initial engineering investment
- Memory Graph synchronization logic is complex — Canon changes must propagate to agent memory with strong consistency guarantees
- Agent lifecycle management adds operational overhead — initialization, scope locking, memory loading, and termination sequencing must be reliable
- Persistent Memory Graphs grow with story universe scale — storage and compute costs scale with entity count and agent session volume
- Debugging agent behavior requires reasoning log analysis, which demands specialized tooling and developer expertise beyond standard application debugging
- The system must manage agent session state across platform restarts and infrastructure events — agent memory persistence requires robust state management infrastructure

## Compliance

Future developers verify this decision is being respected by confirming the following:

1. **AI operations route exclusively through the AI Layer**: No domain module, application module, or integration module may call an AI provider API directly. All AI operations must be requested through the Agent Orchestrator.
2. **Every AI agent has a system identity**: AI agents must be registered actors in the Security Module with defined roles before any operation is performed. Anonymous AI calls are prohibited.
3. **Agent scope is enforced at initialization**: The AI Memory Manager must lock agent memory scope to the assigned Story Universe at agent initialization. Scope cannot be changed without re-initialization through the Agent Orchestrator.
4. **All AI reads and writes are audit-logged**: The AI Audit Logger must record every memory read, every reasoning step, and every proposal submission under the agent's system identity. There is no path to perform an AI operation that bypasses audit logging.
5. **Proposals are never Canon without human confirmation**: AI agent outputs are classified as `AI_PROPOSED` in the Knowledge Graph and may not be promoted to `CANON` status without a creator confirmation event (see ADR-0004).
6. **Architecture review gate**: Any proposal to introduce a new AI capability that does not operate through the AI Layer's Agent Orchestrator and Memory Manager must be escalated to the Chief Software Architect for explicit approval.
