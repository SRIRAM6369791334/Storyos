# ADR-0005: Event-Driven Inter-Module Communication

> **Status:** Accepted
> **Date:** 2026-07-29
> **Deciders:** Chief Software Architect, Lead Developer
> **Supersedes:** None

---

## Context

StoryOS is organized into 19 distinct domain modules, each owning a specific slice of story knowledge and business logic. These modules do not operate in isolation — entity creation in the Character Module must trigger Knowledge Graph registration; a workflow stage transition must trigger a notification; a Canon update must trigger AI Memory synchronization. The question of how modules communicate with each other is one of the most consequential architectural decisions on the platform.

The communication model determines: how easily modules can be developed and tested in isolation, how the system behaves under partial failures, how the platform scales as individual modules grow, and how new modules can be added without modifying existing ones. A poor communication model creates a tightly coupled system where a change to one module ripples through many others — the architectural equivalent of a distributed monolith.

This decision directly determines whether StoryOS's 8-layer, 19-module architecture delivers its promised benefits of isolation and independent evolution, or collapses into an interdependent tangle under the weight of cross-module interactions. It corresponds to **DD-005** in the System Architecture Document (`docs/architecture/architecture.md`) and Architectural Principle P4 (Event Driven).

---

## Alternatives Considered

### Option A: Direct Module-to-Module Synchronous Calls

Modules communicate by calling each other's APIs directly. When a Character Module operation needs to register an entity in the Knowledge Graph, it calls the Knowledge Graph Module's API synchronously. When an entity is created, the Domain Module directly calls the Notification Module, the Audit System, and the Versioning System in sequence. Dependencies between modules are explicit function calls in the code.

**Pros:**
- Simple and immediately understandable — the code explicitly shows what happens when an operation occurs
- Synchronous execution provides strong consistency — every step completes before the next begins
- Straightforward error handling — if the Knowledge Graph call fails, the error is returned immediately to the caller
- No event bus infrastructure required — direct calls work with standard inter-process communication
- Easier to trace execution paths during debugging — stack traces show the complete call chain
- Consistent data state across all modules at every point in the operation — no lag between operation completion and downstream state updates

**Cons:**
- Creates rigid coupling between modules — the Character Module must know the exact API of the Knowledge Graph Module, the Notification Module, and every other module it calls
- A change to any called module's API requires changes in every calling module — cross-cutting changes become expensive and risky
- Cascading failure: if the Notification Module is slow or unavailable, a Character creation operation is blocked or fails — a notification delivery issue becomes a story-writing outage
- Testing a module in isolation requires mocking every module it calls — as call chains grow, test setup complexity explodes
- Independent module scaling is impractical — modules that call each other must be deployed together and scaled together to avoid timeout and connection pool exhaustion issues
- Adding a new consumer of an existing operation (e.g., a new analytics module that needs to know when characters are created) requires modifying the Character Module to add a direct call — every new consumer is a new coupling
- Call chains accumulate latency — a Character creation operation that triggers calls to five downstream modules has a response time that is the sum of all five module response times

---

### Option B: Shared Database as Communication Channel

Modules communicate by writing to and reading from a shared database schema that all modules can access. A module signals state changes by updating records in shared tables that other modules poll. The Character Module writes to a shared `entity_changes` table; the Knowledge Graph Module polls that table for new registrations. Cross-module state is coordinated through shared database state rather than direct calls.

**Pros:**
- No messaging infrastructure required — the database is already present in the architecture
- Operations are durable — if a consuming module is temporarily offline, it reads the state change from the database when it recovers
- Easy to query current state across modules — shared tables are directly queryable for debugging and reporting
- Familiar pattern — many applications coordinate through a shared database
- Atomic writes to the shared coordination table can be done in the same database transaction as the originating operation

**Cons:**
- Violates domain isolation at the most fundamental level — if all modules share database tables, there are no domain boundaries, only organizational convention
- Shared schema creates hidden coupling that is worse than direct API coupling — any module can read or write any shared table, and the schema cannot enforce which module "owns" which data
- Polling is inherently inefficient — consuming modules either poll frequently (high database load) or infrequently (high state propagation lag)
- Schema changes in the shared coordination tables require coordinating changes across every module that reads or writes those tables — the integration complexity of a shared database grows quadratically with module count
- Debugging state propagation issues requires querying database tables rather than inspecting structured event logs — state transitions have no inherent causality record
- Performance under high event volume is poor — a high-throughput story universe generating thousands of entity changes will create polling bottlenecks
- Violates Architectural Principle P5 (Domain Isolated) — domains are supposed to own their data and expose defined interfaces, not share a mutable database
- Horizontal scaling of individual modules is complicated by shared database connection pool management and transaction isolation requirements

---

### Option C: Event-Driven Communication Through Domain Events *(Selected)*

Modules communicate through domain events published to an event bus. When a module completes a significant operation, it emits a structured domain event (e.g., `CharacterCreated`, `CanonUpdated`, `WorkflowStageTransitioned`). Any module that needs to respond to that event subscribes to it through the event bus. The publishing module has no knowledge of who subscribes to its events. Subscribers process events asynchronously and maintain their own local state. Synchronous calls are reserved for operations that require an immediate, authoritative response (e.g., authorization checks, canonical data reads).

**Pros:**
- Publishers and subscribers are decoupled — the Character Module publishes `CharacterCreated` and does not know or care which modules consume it
- Adding a new consumer of an existing event requires zero changes to the publishing module — the new module simply subscribes to the event
- Module failures are isolated — if the Notification Module is slow or offline, it does not block character creation; it processes the event when it recovers
- Each module can be scaled independently — the Knowledge Graph Module can scale to handle high graph-write throughput without coupling to the Character Module's scaling characteristics
- Event log provides a natural, structured record of all significant state transitions — debugging involves inspecting event sequences, not tracing synchronous call chains
- Event schemas are the stable inter-module contract — internal module implementations can change freely as long as emitted events conform to their schema
- Supports replay and reprocessing — a new module can bootstrap its state by replaying historical events from the bus
- Aligns with the AI Layer's requirement to respond to system state changes (Canon updates, workflow stage transitions) without being directly called by domain modules
- Aligns with Architectural Principle P4 (Event Driven) as a foundational platform constraint

**Cons:**
- Introduces eventual consistency for cross-module state — a subscriber's view of a publisher's state may lag by the event processing time
- More complex debugging for end-to-end operation tracing — distributed tracing tooling is required to correlate events across module boundaries
- Event schema evolution requires care — a published event schema is a public contract; changes must be backward-compatible or versioned explicitly
- Event bus infrastructure adds an operational component to manage (availability, throughput, message persistence, dead-letter handling)
- Error handling for event consumers is more complex than synchronous error propagation — failed event processing must be caught, retried, and dead-lettered through the event bus rather than surfaced directly to the calling operation
- Ordering guarantees vary by event bus implementation — operations that depend on strict event ordering require partitioned event streams with careful ordering configuration
- Idempotency: consumers must handle potential duplicate event delivery and implement idempotent processing logic

---

## Decision

All asynchronous inter-module communication in StoryOS uses domain events published through a central event bus. Modules emit structured domain events when they complete significant operations. Consuming modules subscribe to relevant events and process them independently. Direct synchronous module-to-module calls are restricted to authorization verification and canonical data reads, where immediate, authoritative responses are architecturally required.

---

## Rationale

The 19-module architecture described in Section 4 of `architecture.md` only delivers its promised benefits — independent evolution, independent scaling, fault isolation — if modules are genuinely decoupled. Direct module calls and shared database communication are forms of coupling that preserve the form of modular architecture while negating its substance. When a Character Module must call ten downstream modules synchronously, it does not matter that those modules are separately named — the system behaves as a distributed monolith under failure and change scenarios.

Event-driven communication is the mechanism that makes domain isolation real rather than nominal. The Character Module publishes `CharacterCreated` and is done. Everything downstream — Knowledge Graph registration, audit logging, versioning, notifications, AI memory synchronization — happens because those modules subscribe to the event, not because the Character Module knows about them. This is the correct separation: the Character Module is an expert in characters, not in the operational concerns of nine other modules.

The Workflow Layer, AI Layer, and Notification Module specifically require event-driven communication because their job is to observe and respond to system state changes across the entire platform — not to be embedded in every domain module as a direct dependency. An AI agent responding to `CanonUpdated` events operates with architectural clarity. An AI module called synchronously by every Canon write operation is an architectural dependency that spans the entire system.

The eventual consistency trade-off is accepted. The operations most sensitive to consistency — authorization decisions, Canon reads — are kept synchronous. The operations for which lag is acceptable — notifications, search index updates, analytics, AI memory synchronization — are correctly asynchronous.

---

## Consequences

### Positive
- Domain modules are genuinely decoupled — any module can be modified, redeployed, or replaced without modifying any module that publishes events it consumes
- New consumers of existing events (new modules, new AI agents, new analytics capabilities) are added by subscription, not by modifying the publishing module
- Module failures are isolated — a failing Notification Module does not cascade into story creation failures
- Each module scales independently — high Knowledge Graph write demand does not force the Character Module to scale
- The event log provides a structured, queryable history of all significant system state transitions — a powerful debugging and audit resource
- The AI Layer responds to domain events rather than being embedded in domain modules — the AI capability is cleanly separated from story domain logic
- Event replay enables new modules to bootstrap from historical state — powerful for analytics, reporting, and new module onboarding

### Negative / Trade-offs
- Cross-module operations have eventual consistency — a character creation and its Knowledge Graph registration are not atomic from an external observer's perspective
- End-to-end request tracing requires distributed tracing infrastructure — correlating a user action across its event chain requires correlation IDs and structured tracing tooling
- Event schema evolution requires disciplined versioning — breaking changes to event schemas affect all consumers and must be managed as platform-level API changes
- Event bus infrastructure is an additional operational component with its own availability, throughput, and persistence requirements
- Consumer idempotency is a mandatory implementation requirement — all event handlers must be written to handle duplicate delivery correctly
- Dead-letter queue management is operationally significant — failed events must be monitored, diagnosed, and reprocessed; the dead-letter queue is a routine operational concern, not an edge case
- Developers familiar with synchronous request-response programming must adapt to event-driven thinking — onboarding time increases for engineers without event-driven experience

## Compliance

Future developers verify this decision is being respected by confirming the following:

1. **Cross-module asynchronous communication uses the event bus**: No domain module may import or call another domain module directly for asynchronous operations. All cross-module state change notifications must be mediated through domain events on the event bus.
2. **Synchronous direct calls are restricted to defined cases**: Direct synchronous calls between modules are permitted only for: (a) Security Module authorization checks, and (b) Knowledge Layer canonical data reads. All other cross-module communication must be event-based.
3. **Domain events are schema-versioned**: Every domain event type must have a documented schema version. Event schema changes that remove or rename fields must be treated as breaking changes and handled through event versioning, not in-place modification.
4. **All event consumers implement idempotent processing**: Module developers must design event handlers to produce the same result when processing the same event twice. Idempotency must be verified in unit tests for every event handler.
5. **Dead-letter queues are monitored**: Operations tooling must include alerting on dead-letter queue growth. Dead-lettered events must be reviewed and reprocessed or explicitly discarded with a logged justification.
6. **Architecture review gate**: Any new module design must document its event subscriptions (what events it consumes) and event publications (what events it emits) before module implementation begins. Modules that propose direct calls to other domain modules for asynchronous operations must be redesigned to use events.
